# 5. Устройство порта и проверка точности

## 5.1. Почему «гибрид», а не переписывание с нуля

Главное требование — точное совпадение логики с Amiga. Разбор показал, что
оригинальный код:

* хранит всё состояние по абсолютным адресам (карта $11928, списки объектов,
  десятки флагов в $112xx–$114xx) и передаёт данные между подпрограммами через
  регистры и флаги условий 68000;
* на краях карты читает и пишет соседнюю память (строку над картой, переменные
  после неё) — это часть поведения, а не ошибка, которую можно «исправить»;
* перемешивает логику и отрисовку (блиттер рисует прямо во время обработки
  объектов).

Поэтому выбран гибридный путь: каждая подпрограмма 68000 переводится в функцию
C++ один к одному, данные остаются в эмулированной памяти по оригинальным
адресам, а «железо» реализуется нативно.

## 5.3. Транслятор 68000 → C++

`tools/m68k2cpp.py` + конфигурация `tools/translate.json` и аннотации
`tools/annotations.json`:

1. **Декодер** (`tools/m68kdec.py`) — собственный декодер всех инструкций 68000
   (проверен на всех 8255 инструкциях программы против capstone).
2. **Поиск кода** рекурсивным обходом от точек входа, таблиц переходов
   ($11900 — обработчики движения Murphy, $1B422 — зоны меню, $11210 —
   анимация зонков/инфотронов, $10D24 — эффекты музыки) и констант-адресов кода
   (`movea.l #$E3E2,a6` + `jmp (a6)`).
3. **Разбиение на функции**: у каждой подпрограммы своя C++-функция; переход в
   чужую точку входа — хвостовой вызов; общие «хвосты» дублируются.
   `jmp (An)` — `switch` по меткам функции с запасным вызовом через диспетчер
   `callAddress`.
4. **Живость флагов**: флаги вычисляются только там, где их кто-то читает
   (межпроцедурный анализ: флаги, возвращаемые подпрограммой вызывающему, тоже
   учитываются). Остальные инструкции превращаются в обычный C.
5. **Генерация**: одна строка C++ на инструкцию, в комментарии — адрес и
   исходная инструкция; имена подпрограмм и переменных берутся из аннотаций.

Пример (начало `game_frame`, $B5A4):

```cpp
void game_frame() {
L_00B5A4:
    logic<1>(rd8(A5 + 0x6));  // 00B5A4  tst.b 6(a5)
    if (CC_NE) goto L_00B5A4;  // 00B5A8  bne $b5a4
    push32(0xB5AE); sound_frame(); A7 += 4;  // 00B5AA  bsr $10104
    ...
    wr8(v_frame_div50, (rd8(v_frame_div50) + 0x1));  // 00B5B6  addq.b #$1, $11294.l
```

Вызовы подпрограмм кладут на эмулированный стек тот же адрес возврата, что и
68000, так что содержимое стека совпадает с оригиналом.

Перегенерация: `python3 tools/m68k2cpp.py tools/translate.json` (C++),
`python3 tools/m68kdis.py tools/translate.json disasm` (листинг).

## 5.4. Модель времени

Игра синхронизируется исключительно опросом положения луча
(`VPOSR/VHPOSR`) и ожиданием кнопок/клавиатуры. В порте (и в эталонном
эмуляторе) время идёт так:

* каждое чтение `VPOSR`/`VHPOSR` продвигает луч на одну строку (313 строк в
  кадре PAL);
* каждое другое чтение регистров железа (порты CIA, `JOYxDAT`, `POTGOR`,
  `INTENAR/INTREQR`) — на 16 тактов (1/14 строки), поэтому циклы вида «ждать
  отпускания кнопки» завершаются;
* блиттер выполняет операцию мгновенно (`DMACONR` никогда не показывает
  «занят»);
* при переходе луча со строки 312 на 0 кадр готов: фронтенд показывает
  картинку, отдаёт звук, опрашивает ввод и ждёт до следующих 20,03 мс; затем
  выставляется прерывание кадровой развёртки.

Так один проход игрового цикла (`game_frame`) занимает ровно один кадр, как на
Amiga, а поведение не зависит от скорости ПК.

Изображение строится построчно по мере движения луча: copper исполняется в
тактах цвета (поддерживаются смены цвета посреди строки, как в меню), битовые
плоскости выбираются по DDFSTRT/DDFSTOP с учётом модулей и тонкого скролла
BPLCON1, спрайт курсора — в режиме lowres поверх полей.

## 5.5. Эталон и сравнение

* `port/tests/refemu.*` — эталонный эмулятор: **оригинальный** код 68000
  (из образа дискеты) выполняется на ядре Musashi поверх того же «железа».
  Дисковые функции заменены теми же нативными реализациями, что и в порте.
* `refrun` — прогон эталона с дампом кадров (PPM) и сценарием ввода.
* `difftest` — эталон и порт в одном процессе (порт в отдельном потоке,
  передача управления на границе кадра). После каждого кадра сравнивается
  вся chip-RAM, кроме стека ($7F000–$7FFFF: там лежат кадры прерываний с
  неизвестным порту адресом возврата), и выходная картинка.
* `--random SEED` — случайный джойстик/огонь (фаззинг), `--level L` —
  одинаковая «подстановка» уровня в меню обеих машин, `--coverage` — покрытие
  исполненного кода эталона.
* `difftest_trace` — отладочный вариант: сгенерированный код с метками адресов,
  `--trace-frame F` пишет трассы PC обеих сторон, `--watch ADDR` показывает
  каждую запись по адресу с историей PC.

Найденные таким образом ошибки перевода исправлены в трансляторе (а не в
сгенерированном коде), поэтому генерация остаётся воспроизводимой.

## 5.6. Что сделано нативно (и почему это не влияет на логику)

| Оригинал | В порте |
|---|---|
| загрузчик файлов OFS из крэка ($10404, в интро $54264) | `native_loadFile`: тот же номер файла → тот же PHIL_xx из ADF, D0=0, Z=1 |
| управление мотором/задержки дисковода ($1035E, $103C2, $10A56) | пустые функции |
| запись рекордов на дискету ($7000, код крэка) | `native_saveHiscores`: 2048 байт в файл сохранения |
| защита Copylock ($84F4) | уже удалена крэком (`clr.w $BE; rts`) |
| блиттер, copper, спрайты, Paula, CIA | нативная реализация в `port/src/amiga/` |
